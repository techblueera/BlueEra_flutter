PART 1 — WHAT WAS ACTUALLY WRONG
================================================================================

1.1  "NEW PACKAGE / NEW LAYER"
--------------------------------------------------------------------------------
  A call was not a screen. It was a second app.

  android/app/src/main/AndroidManifest.xml declared:

      <activity android:name=".CallActivity"
          android:taskAffinity="ai.bluecs.app.calling"
          android:label="Voice Call" ... />

  CallActivity.kt overrode:

      override fun getDartEntrypointFunctionName(): String = "callMain"

  So every call started a SECOND FlutterEngine + SECOND Dart isolate in a
  SEPARATE Android task. callMainImpl() re-ran the whole boot each time:
  projectKeys -> firebaseInitializeApp -> Hive.initFlutter -> 4 secure-storage
  reads -> Get.put(CallController) -> a second socket connection.

  That is the ~1-2s delay and the separate "Voice Call" card in Recents.


1.2  "KILLED MODE MAKES A NEW APP"
--------------------------------------------------------------------------------
  The killed-state accept booted the app TWICE:

    1. CallActionReceiver.kt  -> getLaunchIntentForPackage()
                              -> MainActivity cold start, full main()
    2. main.dart cold-start check -> callController.acceptCall(...)
    3. call_controller.dart       -> launchCallActivity(...)
                              -> CallActivity cold start, full callMain()

  Result: two engines, two isolates, two GetX containers, two CallControllers,
  TWO AUTHENTICATED SOCKETS for the same user, two Recents cards.

  The codebase was already full of workarounds for this — cross-isolate
  mailboxes written to secure storage because "statics can't be used, the two
  engines are different Dart isolates".


1.3  SPEAKER
--------------------------------------------------------------------------------
  ROOT CAUSE: flutter_webrtc keeps audio routing in a process-wide static that
  every engine attach overwrites.

    FlutterWebRTCPlugin.java:115
        AudioSwitchManager.instance = new AudioSwitchManager(context);

  The app has several engines that all register flutter_webrtc:
      - MainActivity
      - CallActivity              (until this change)
      - FCM background isolate    (new FlutterEngine(ctx) auto-registers plugins)
      - flutter_overlay_window    (FlutterEngineGroup)

  When any of them attached mid-call, the singleton was replaced by a fresh
  instance that was NEVER activate()d. Every later Helper.selectAudioOutput()
  was recorded but never applied.

  Nothing threw. And the UI set isSpeakerOn BEFORE the native call:

      currentAudioRoute.value = route;
      isSpeakerOn.value = route == AudioRoute.speaker;   <-- UI flips here
      try { await Helper.selectAudioOutput('speaker'); }
      catch (e) { if (kDebugMode) print(...); }          <-- invisible in release

  So the button lit up while audio stayed on the earpiece.

  An FCM data message during a call is enough to trigger this — and call
  signalling itself arrives over FCM, so it was not an edge case.


1.4  MUTE
--------------------------------------------------------------------------------
  toggleMic() only touched:

      localStream?.getAudioTracks().firstOrNull
      if (audioTrack == null) return;    <-- silent, UI does not even move

  Three failure modes:
    a) Wrong engine — the main engine's localStream was null while the other
       engine owned the call, so any main-engine Mute button did nothing.
    b) Missed senders — after a renegotiation the sender's track is not the
       same object as localStream's first audio track.
    c) Audio->video switch re-enabled tracks and never re-applied isMicOn, so
       a muted mic silently went live again.


1.5  BONUS BUG — isCallActivityActive reset on every resume
--------------------------------------------------------------------------------
  app_lifecycle_handler.dart blanked the flag unconditionally on resume.
  Switching from the "Voice Call" card back to the app card therefore told the
  main engine it owned the call: it resumed handling call:ended /
  call:cancelled / call:incoming for a call in the other engine, and the
  `detached` branch would then endCall() a live call.

FIX 1 — SPEAKER: honest state + self-healing route
--------------------------------------------------------------------------------
  NEW  android/app/src/main/kotlin/com/example/bluehrmobileapp/CallAudioBridge.kt
       Talks to AudioSwitchManager.instance directly.
         - re-ACTIVATES whichever instance is current before selecting

         - READS THE SELECTION BACK so Dart can show the true route

       `implementation` dep of the plugin and is not on the app module's

FOLLOW-UP — LOCK-SCREEN RING
--------------------------------------------------------------------------------
  setCallWindowActive was first wired into _setupLocalMedia, which only runs on
  ACCEPT — too late for a ring to show on a locked screen.

  It is now a worker on callStatus, registered in onInit:

      _callWindowWorker = ever(callStatus, (CallStatus status) {
        _setCallWindowActive(
            status != CallStatus.idle && status != CallStatus.ended);
      });

  Why a worker instead of a call in _handleIncomingCall: five places put the
  controller into a live state and would all need the same line —
      :725  outgoing
      :828  incoming ring
      :942  accepting   (the cold-start / killed-state accept path)
      :1083 connecting
      :3837 CallKit listener ring
  One worker covers incoming, outgoing, fare-call, rider order and killed-state
  accept with nothing to keep in sync.

  _setCallWindowActive dedupes against a _callWindowActive mirror, so a call
  moving ringing -> accepting -> connecting -> connected hits the channel once,
  not four times.

  ORDERING CHECK: in _handleIncomingCall, callStatus = ringing is at :828; the
  background branch that posts the full-screen-intent notification is ~25 lines
  below. So setShowWhenLocked(true) reaches the Activity BEFORE the notification
  that raises it. The channel is serviced on the platform thread regardless of
  whether the Activity is paused, so this works from background too.


FEATURE — WHATSAPP-STYLE TOP CALL STRIP  (+ the emergency fixes that followed)
--------------------------------------------------------------------------------

  WHAT IT DOES
    A green bar pinned to the top of EVERY screen whenever a call is live and
    the user is not on the call screen:

      +----------------------------------------------------+
      | (P)  01:23 . Tap to return to call      [ End ]     |   #00A884
      +----------------------------------------------------+
      |                                                    |
      |            whatever screen you are on              |

      - tap the bar   -> back into the call room
      - tap End       -> hangs up right there, without going back in first
      - label adapts  -> "Calling..." / "Connecting..." / live duration

    It is the ONLY "tap to return to call" affordance in the app now. See
    "ONE AFFORDANCE, NOT THREE" below.


  ~~~ THE THREE BUGS THE FIRST CUT SHIPPED WITH ~~~

  All three had ONE root cause: a killed-state call accept replaced the app's
  `home` with the call screen.

      main.dart:
          home: Obx(() {
            if (CallController.launchedForCall.value) {
              return const CallActivityRoomScreen();   // <-- the whole problem
            }

  Everything that went wrong followed from it:

    "Back closes the app"
        The call screen was `home`, so there was nothing beneath it to pop to.
        Back therefore fell through to Picture-in-Picture, and dismissing PiP
        exits the app.

    "Can't use the app while a call is on"
        `home` WAS the call. There was no app behind it to go back to.

    "Close and reopen -> goes straight to the call"
        `launchedForCall` was still true, so `home` still resolved to the call
        screen.

    "Call cut, reopen -> BLANK page, app unusable"
        Worst case of the same thing. After the call ended `launchedForCall`
        was still true and callStatus was idle — and the call screen renders
        an empty SizedBox for idle. So `home` was a blank page with no way out
        except force-quitting.


  ~~~ THE FIXES ~~~

  1. THE `home` HIJACK IS GONE
       main.dart always boots the app normally now. The call room is PUSHED on
       top of it like any other screen.

       Removed with it:
         - CallController.launchedForCall            (the Rx behind the hijack)
         - CallController._coldStartCall             (only fed the hijack)
         - two `launchedForCall` bail-outs in splash_screen.dart, which used to
           skip normal navigation and would now strand the user on splash
         - markColdStartCall() kept as a no-op so main.dart's three killed-state
           accept paths still read the same

  2. NEW  CallController._openCallRoom()
       Pushes /CallRoomScreen on top of whatever is showing, and RETRIES on a
       250ms cadence (~10s ceiling) because on a cold start:
         - the navigator may not exist yet (accept runs during app init), and
         - splash does its own pushNamedAndRemoveUntil shortly after, which
           would wipe a push issued too early.
       It waits for the route to leave splash, then pushes once and stops.
       Called from acceptCall and _handleCallAccepted.

  3. PICTURE-IN-PICTURE REMOVED
       Requested, and it was the mechanism behind "Back closes the app".

       Dart:
         - the call screen's PiP branch, _buildPipModeView (~35 lines),
           _enterPipMode, _isInPipMode, and the PiP listeners in initState
         - the three "minimise" buttons now call a new _minimiseCall() which
           pops (or lands on the bottom nav if there is nothing to pop)
         - call_pip_service.dart -> RENAMED to call_window_service.dart
           (CallPipService -> CallWindowService). It kept only
           setCallWindowActive; a class called "PipService" with no PiP left
           in it would have been a lie.

       Kotlin (MainActivity):
         - enterCallPipMode(), the Mute/Hang-Up RemoteActions, the PiP action
           BroadcastReceiver + its register/unregister, ACTION_CALL_MUTE_TOGGLE,
           ACTION_CALL_HANGUP, onPictureInPictureModeChanged, isInCallPip
         - onUserLeaveHint no longer shrinks a call into PiP on Home. The call
           keeps running in the background (foreground service + the floating
           overlay) and the strip is the way back.
         - setCallWindowActive KEPT — that is the lock-screen / keep-screen-on
           behaviour, which is unrelated to PiP and still needed.
         - the video-player PiP (isPipEnabled) is untouched.

       Back now always minimises to the strip. If there is genuinely nothing
       beneath (the push lost a race with splash) it lands on the bottom nav
       rather than leaving the user stuck.

  4. THE STRIP SHOWED ON THE CALL PAGE ITSELF
       Visibility was a single bool set in initState / cleared in dispose.
       But `/IncomingCallScreen` and `/CallRoomScreen` render the SAME widget,
       and on Get.offNamed between them Flutter runs the new screen's initState
       BEFORE the old screen's dispose. The trailing dispose set the bool back
       to false while the call screen was still on top.

       Now a COUNTER: CallController.callScreensMounted (+ callScreenMounted() /
       callScreenUnmounted()). Strip shows only at zero.

  5. THE STRIP FLASHED BEFORE THE CALL SCREEN APPEARED
       Caught during the flow audit, not on device. There are three windows
       where a call is live but its screen has not mounted yet:
         - an outgoing call between callStatus=outgoing and the API/ICE setup
           finishing
         - an accept between callStatus=accepting and the accept round-trip
         - a killed-state accept, for the whole boot (strip over the splash)

       Added CallController.callRoomEverShown: the strip only appears once the
       call screen has been shown at least once for THIS call. Semantically
       right — the strip is for RETURNING to a call you have already seen — and
       it closes all three windows with one condition instead of three patches.


  ~~~ ONE AFFORDANCE, NOT THREE ~~~

  There were three "tap to return to call" widgets. Two are deleted; the strip
  is the only one left, so the whole app stays traversable during a call.

    DELETED  lib/features/common/connect/widget/ongoing_call_banner.dart
             The Connect tab banner (rendered twice — Chat and Inquiry tabs).

    DELETED  lib/features/chat/view/widget/ongoing_call_message_card.dart
             The in-chat "Ongoing call" bubble. Removing it also meant removing
             what fed it:
               - the synthetic `callongoing` message injected at the bottom of
                 the reversed message list (personal_chat_screen.dart)
               - its 2-second poll of the active-call record (_pollOngoingCall,
                 _ongoingCallActive, _ongoingCallPoll)
               - the `case "callongoing":` branch in message_card.dart


  ~~~ FINAL STRIP CONDITIONS ~~~

    SHOWN when ALL of:
      - callRoomEverShown        (call screen seen at least once this call)
      - callScreensMounted == 0  (not on the call screen right now)
      - !isFareCall              (fare calls / rider orders keep their own UI)
      - callStatus in { outgoing, accepting, connecting, connected }

    HIDDEN for:
      - ringing   an unanswered incoming call owns the full screen. Back is
                  SWALLOWED there so the user cannot strand a ringing call with
                  no way back — accept or decline, same as WhatsApp.
      - idle / ended
      - fare calls and rider orders

  Note on Obx: shouldShow reads the two static observables FIRST, before the
  Get.isRegistered check. Bail out before touching any observable and Obx
  throws "improper use of a Obx" — its builder must track something.

PART 2B — SECOND ROUND OF CALL FIXES (reported from screenshots + video)
================================================================================

  Reported as:
    - Decline button unresponsive
    - Accept inconsistent, freezes on the app opening animation
    - Message disconnects immediately instead of offering a quick reply
    - Notification must persist in the tray while ringing
    - Caller shows "Unknown" when the app is opened from the notification

R1. DECLINE DEAD / ACCEPT FLAKY — the wrong notification was winning
--------------------------------------------------------------------------------
  TWO incoming-call notifications existed and the app tried the broken one
  FIRST. showIncomingCallLocalNotification() attempted a native RemoteViews
  notification over a MethodChannel, and only fell back to
  flutter_local_notifications when that channel was unavailable (i.e. the FCM
  background isolate). So whenever the main engine was alive — the common case —
  the broken path is the one that ran.

  The native notification's buttons went to CallActionReceiver.kt:

      ACTION_DECLINE -> {
          savePendingAction(context, "decline", callId, roomId, callType)
          // Intentionally NOT calling launchApp()
      }

  It writes a SharedPreferences flag and stops. THE SERVER IS NEVER TOLD, so the
  caller keeps ringing — and because decline deliberately does not open the app,
  nothing ever consumes the flag. Decline was a no-op by construction.

  Accept called getLaunchIntentForPackage() + CLEAR_TOP, a raw relaunch — the
  "stuck on the opening animation".

  Meanwhile the flutter_local_notifications path ALREADY had working handlers:
    - onForegroundNotificationResponse  → declineCall() / acceptCall() in-process
    - onBackgroundNotificationResponse  → a real REST POST call/decline that
                                          works with the app killed

  FIX: the native attempt is gone. One notification path in every state.
       Accept now goes through `showsUserInterface: true` — the plugin's
       supported launch path — instead of a hand-rolled intent.

  NOTE: CallActionReceiver.kt, its manifest entry and
  readAndClearPendingNativeCallAction() in main.dart are now unreachable for
  calls. Left in place as harmless dead code in case the nicer native buttons
  are wanted back — but the receiver would need a REAL decline first, not a
  stashed flag.


R2. "MESSAGE" WAS A SECOND, MISLABELLED DECLINE
--------------------------------------------------------------------------------
  onTap was literally `controller.declineCall()`.

  FIX: opens a sheet with four canned reasons ("Can't talk right now", "I'll
  call you back", "I'm in a meeting", "Call me later") plus a free-text field.

  NEW  CallController.declineWithMessage(text)
       Sends the message and THEN declines. That order is load-bearing:
       declineCall() runs _cleanup(), which wipes conversationId and the remote
       user id, so sending afterwards would have nothing to address it to.
       Uses sendInitialMessage when no thread exists yet (a call from someone
       never chatted with) and sendMessage otherwise. A send failure still
       declines — failing to deliver the note must never leave a call ringing.

  The ringtone stops when the sheet opens; the call stays live until a reason is
  picked, and dismissing the sheet leaves the call untouched.


R3. CALLER SHOWS "Unknown"
--------------------------------------------------------------------------------
  TWO bugs in initStateFromCallKitExtra, either of which produces it:

      if (callStatus.value != CallStatus.idle || extra.isEmpty) return;   // 1
      ...
      if (senderId.isNotEmpty) {                                          // 2
          callerName.value = extra['callerName'] ?? '';
          ...   // callId and roomId live in here too

    1. It bailed on ANY non-idle status — including `ringing`, which is exactly
       what the socket's call:incoming leaves us in. The thin socket payload
       (often nameless) landed first and set ringing; the richer push payload
       that DID carry the name was then discarded.

    2. Every field — name, image, callId, roomId — sat inside
       `if (senderId.isNotEmpty)`. A payload without senderId (a socket event
       with no `initiated_by`) applied literally nothing.

  FIX: rewritten as a MERGE.
    - bails only when a DIFFERENT call is already past ringing
    - applies identity fields unconditionally
    - a pick() helper means a later, thinner payload can never blank a field an
      earlier one filled; a literal "Unknown" is treated as empty


R4. MISSING ONGOING-CALL INDICATOR BAR
--------------------------------------------------------------------------------
  bottom_navigation_bar_screen.dart reserved space for a bar that never existed:

      if (hasActiveCall) topOffset = 50;     // 50px of nothing

  The widget it was reserving for was the commented-out OngoingCallOverlay in
  main.dart — the same placeholder the top strip replaced. So a live call just
  left a 50px empty band at the top of every tab.

  FIX: branch removed. The strip is the indicator and pushes the app down
       itself; keeping this would have double-gapped.

  NOTE: the strip is GREEN (#00A884, WhatsApp's colour) per the "same ditto like
  whatsapp" spec, not red. Trivial to change if red is wanted.


R5. NOTIFICATION PERSISTENCE — NOT FIXED
--------------------------------------------------------------------------------
  Could not reproduce from the code. The flags are already correct on the path
  now in use (ongoing: true, autoCancel: false, FLAG_INSISTENT) and every
  cancelIncomingCallLocalNotification() call traced fires on a legitimate event
  (accept, decline, call cancelled, call ended, screen opened).

  Plausible that the NATIVE notification — the broken one — was what was being
  cancelled, in which case R1 fixed this as a side effect. Retest decides.

  If it still vanishes, the two things needed to diagnose:
    - does it go IMMEDIATELY on swipe, or after a delay?
    - Android version — 14+ made ongoing notifications user-dismissible, which
      would move the fix to a foreground service.

PART 2C — AUDIO → VIDEO SWITCH
================================================================================

  Reported as: raw text in the toast, blank view after switching, black screen
  after the other side approves.


V1. THE TOAST WAS AN UNTRANSLATED KEY, NOT A SPACING BUG
--------------------------------------------------------------------------------
  The screenshot showed the literal string "waitingForApprovalToSwitchVideo",
  broken mid-word. AppStrings stores key-as-value:

      static const String waitingForApprovalToSwitchVideo =
          "waitingForApprovalToSwitchVideo";

  `.tr` looks the key up in assets/translations/en.json and returns the raw
  string when absent. Its neighbours were all present; two were missed:

      waitingForApprovalToSwitchVideo    MISSING → added
      cameraPermissionRequiredToSwitch   MISSING → added

  No layout change needed: the mid-word break was camelCase having no spaces to
  break on. Real prose wraps normally.

  ⚠ SCOPE: 2,539 of 7,021 AppStrings entries are key-as-value. Any other one
  missing from en.json surfaces exactly the same way. Only the two hit here were
  fixed — a script diffing AppStrings against en.json would find the rest.


V2. BLANK LOCAL PREVIEW — the renderer was never created
--------------------------------------------------------------------------------
  _setupLocalMedia only builds a renderer when the call STARTS as video:

      if (isVideo) { localRenderer = RTCVideoRenderer(); await ...initialize(); }

  So on an audio → video switch it is still null, and _enableLocalVideo did:

      localRenderer?.srcObject = localStream;    // null-safe → silent no-op

  Camera capturing, nothing rendering it.

  FIX: _ensureLocalRenderer(), called at the top of _enableLocalVideo, plus the
       srcObject assignment on the already-has-a-track path, which was missing
       it too.


V3. BLACK SCREEN AFTER APPROVAL — no renegotiation existed at all
--------------------------------------------------------------------------------
  `grep onRenegotiationNeeded` across the controller returns NOTHING.

  _enableLocalVideo does pc.addTrack(videoTrack, localStream!) on an already-
  established peer connection, which requires a fresh offer/answer before the
  far end gets a video m-line. Nobody sent one — so the remote never received
  video and both sides sat black.

  FIX: _renegotiateAfterMediaChange().
    - only the ORIGINAL CALLER re-offers. Both ends know who that is from
      isCaller, and two simultaneous offers would collide (glare). The callee's
      video still gets through — it rides in the answer.
    - 600ms settle delay: both sides run _enableLocalVideo off the same
      call:type-switched event, so offering immediately races the callee's
      addTrack and yields one-way video.

  ⚠ LEAST VERIFIABLE CHANGE IN THE WHOLE SESSION. Live WebRTC renegotiation
    cannot be confirmed by building. Two symptoms to watch:
      - ONE-WAY VIDEO      → 600ms too short, or the answer is not carrying the

PART 2D — NETWORK LOSS DURING A CALL
================================================================================

  Reported as: incoming call + network drop freezes on a black screen; the other
  participant is left in a ghost call; calls should auto-terminate after 10s.

  ROOT CAUSE, one line:

      case RTCPeerConnectionState.RTCPeerConnectionStateDisconnected:
        print('⚠️ PEER DISCONNECTED (may reconnect), peer=$peerId');
        break;                       // ← and nothing else

  `_peerDisconnectTimer` was DECLARED, and CANCELLED IN THREE PLACES, but NEVER
  ONCE STARTED. A network drop was logged and then ignored: no teardown, no
  timeout, no UI change. Nothing anywhere watched the device's own connectivity
  during a call either.

  N1. INCOMING CALL + DROP → BLACK SCREEN
      Connectivity is now watched for the WHOLE life of a call, from the first
      ring — hung off the callStatus worker, not _setupLocalMedia. The latter
      only runs on ACCEPT, so it would have missed exactly the reported case:
      losing signal while ringing, where there is no peer connection yet to
      notice anything.

      While `ringing` or `outgoing`, a transport loss ABANDONS IMMEDIATELY
      rather than waiting 10s — there is no media path to resume and no way to
      reach the server to accept, so waiting is just 10s of frozen screen. It
      dismisses the UI, cancels the notification, stops the ringtone, and says
      "Call ended — no internet connection".

  N2. GHOST CALL ON THE OTHER SIDE
      RTCPeerConnectionStateDisconnected now arms the grace timer. ICE
      `disconnected` is genuinely recoverable so it does not kill the call
      outright, but after 10s the far end tears down instead of sitting there
      with a running timer and no audio.

      This half works with NO BACKEND CHANGE — the surviving side detects it.

  N3. THE 10-SECOND RULE
      One _networkGracePeriod = 10s, used by both the local-radio and peer-ICE
      paths. Cancelled on reconnect (which also kicks the socket back up) and on
      any transition back to connected. The call screen shows "Reconnecting…" in
      amber during the window instead of a ticking timer over a dead connection
      — which is what read as a freeze.

      On expiry: best-effort POST call/end with end_reason: "network_error"
      (4s timeout — we are probably still offline and an untimed request would
      hold teardown open behind a connection that is not coming back),
      best-effort socket leave, then local teardown regardless.

  ⚠ REGRESSION RISK: a brief drop (< 10s) must let the call SURVIVE. An
    over-eager timer killing healthy calls is the failure mode to watch for.

PART 2E — BUSY SIGNAL
================================================================================

  Reported as: calling someone already on a call should say "user is busy", not
  ring out.

  The callee's app was throwing the second call away silently:

      if (callStatus.value != CallStatus.idle) return;   // already in a call

  So the SERVER never learned B was busy. A rang for the full 30-second timer
  and was then told "No answer" — when the truthful answer was available the
  instant the second call arrived.

  Everything else was already in place: CallRingingState.busy exists,
  fromServer("busy") parses it, its label is "User is busy", isTerminal is true
  so the outgoing screen auto-dismisses after 2s. The only missing link was the
  callee telling anyone.

  FIX: _rejectAsBusy(data) declines the SECOND call with reason: "busy".
    - touches NONE of our own call state. The ids in the payload belong to the
      INCOMING call — calling declineCall() would have used them to tear down
      the call actually in progress.
    - ignores a re-delivery of the same call (socket + FCM both deliver
      call:incoming), so it bails when callId matches the live call or is empty.
    - silences the second call's ring: the FCM background isolate has its own
      controller state and may already have posted a notification / CallKit UI,
      which would otherwise ring on top of a call in progress.

  ALREADY WORKING: 409 on POST call/initiate is handled — the caller shows "User
  is busy on another call". That covers the case where the server ALREADY knows
  B is engaged. This fix covers the case where it does not: a race between two
  calls, or B on a call the server has not marked busy.

PART 2F — BACKEND WORK REQUIRED
================================================================================

  Written up in full: docs/backend/CALL_SIGNALLING_BACKEND_UPDATES.md

  Both items are ADDITIVE — the app ships ahead of them and degrades sanely.

  1. PARTICIPANT-DROP TIMEOUT  (the app CANNOT do this)
     An offline device cannot tell the server anything, so the teardown POST is
     issued while still offline and will usually fail. Without a server-side
     timeout the call record stays open forever and BOTH users' call logs are
     wrong.

     Needed: socket leaves an active call room and does not rejoin within 10s
     → mark ended with end_reason "network_error", emit call:ended to the rest,
     write the log with the real duration. Plus idempotent handling of a late
     duplicate call/end from a recovering client.

  2. HONOUR reason: "busy" ON DECLINE
     Relay it as ringing state `busy`, not `declined`, and log the call as
     busy/rejected rather than missed.
     Degradation if never shipped: the caller sees "Call declined" instead of
     "User is busy". Wrong word, right timing.

  OPEN QUESTION for the backend team (in the doc): is there an existing
  presence/heartbeat on the call room to hang the 10s timer off? A raw socket
  `disconnect` also fires on healthy transport upgrades and cell handovers, so
  using it naively would end calls that were fine.

PART 7 — NON-CALL FIXES IN THE SAME WORKING TREE
================================================================================

Not call work, but they are in this branch and will land in the same commit.

  LOGIN NO LONGER LOST ON A FAILED PROFILE FETCH
      `isUserLogin` was ONLY ever written inside the profile-apply methods
      (SharedPreferenceUtils.userLoggedInBusiness / userLoggedInIndividualGuest),
      which run only on a SUCCESSFUL fetch. A login whose profile fetch failed —
      e.g. verify-otp returning `business: null` / `business_id: null`, leaving
      nothing to fetch with — kept a valid token but never flipped the flag, so
      the next launch read it as "false" and forced a full re-login.
      Now written in verifyOTP beside the authToken, for both account types.
      Files: lib/features/common/auth/controller/auth_controller.dart

  "ME" TAB NO LONGER SHIMMERS FOREVER
      The tab keys off the type global being empty, and a FAILED fetch leaves it
      empty exactly like one still in flight — so a failed profile load was an
      infinite loader with no way out. Added meProfileError to both profile
      controllers and a _MeTabError state with a retry AND the hamburger →
      ProfileMenuDrawer, because Logout only lives in that drawer and an account
      whose profile will not load is exactly the account that needs it.
      Files: bottom_navigation_bar_screen.dart, view_business_details_controller,
             view_personal_details_controller

      ⚠ FOLLOW-UP ALREADY HIT ONCE: the individual guard was first written as
      `if (userId.isEmpty) return;` — wrong twice over. The endpoint is keyed on
      PHONE (`user-service/user/get?contact_no=$userMobileGlobal`), and `userId`
      is only populated BY that response, so on a fresh login the guard blocked
      the very fetch that would fill it. Now guards on userMobileGlobal. If that
      error screen shows on a healthy account, suspect the guard before the
      network.

  CHAT REAL-TIME (pre-existing, not caused by the call work)
      ChatSocketService.disposeSocket() CLEARS _registeredListeners outright, so
      onConnect has nothing to replay — and the only thing that re-ran
      ChatViewController.connectSocket() was an app RESUME. The bottom-nav host
      disposes the socket on any root re-navigation (returning from a call, a
      notification renav, offAllNamed), after which live chat was dead until the
      user backgrounded and reopened the app.
      Calls already had a fix for this exact problem (onCallListenersRebind);
      chat did not. Mirrored it: onChatListenersRebind +
      ensureChatSocketListeners().
      Files: chat_socket.dart, chat_view_controller.dart
      TEST: open a chat, take a call (or any root re-nav), come back, then have
      someone message you WITHOUT backgrounding the app.

  RIDER AADHAAR — THREE STATES  (docs/backend/RIDER_AADHAAR_VERIFIED_APP_GUIDE.md)
      _applyAadhaarStageFromRiderStatus rendered a verified tick from `aadhar`,
      which means "an Aadhaar has been provided", not "verified" — the bug that
      guide says told 1,591 riders they were done when they were still pending.
      Now entry / pending / rejected / verified, using aadharVerified with the
      guide's interim `aadharVerifiedThrough != null` fallback so it works
      before the be_rider_service deploy. Display uses `aadharMasked`, never
      `aadharNo` (null on the OTP route by design).
      Left alone deliberately: stepStatus still reads `aadhar` (it is the
      "submitted" checklist, a different axis), and the go-live gate already
      correctly uses verificationStatus == "approved".
