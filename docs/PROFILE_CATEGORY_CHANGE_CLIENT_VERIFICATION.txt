1. THE ME TAB RE-ROUTES CORRECTLY — VERIFIED
================================================================================

The headline risk was that changing category would leave a merchant on the OLD
per-type dashboard (a grocer who became a restaurant still seeing GroceryScreen).
It will not, PROVIDED §8.1 is followed exactly. Traced end to end:

  BUSINESS
    viewBusinessProfile()
      -> _applyBusinessProfile()
      -> SharedPreferenceUtils.userLoggedInBusiness(...)   :454
           writes businessCategory / businessSubCategory / businessType
      -> getUserLoginData()                                :471
           re-reads all 18 keys and repopulates the globals
      -> isBusinessProfileReady / isMeProfileFetching flip  :474
      -> resolveBusinessScreen()'s Obx re-runs _buildBusinessScreen()
           against the NEW globals -> the new per-type screen

  INDIVIDUAL
    viewPersonalProfile()
      -> SharedPreferenceUtils.userLoggedInIndividualGuest(profileType,
         profession, designation, ...)
      -> getUserLoginData()                                :1052
      -> resolveIndividualScreen() re-runs _buildIndividualScreen()

So a plain profile re-fetch is sufficient. No extra invalidation call is needed
for the Me tab itself.

  >>> §8.1's "Don't patch it locally" is LOAD-BEARING FOR US, not hygiene.

  `businessCategoryGlobal`, `businessTypeGlobal`, `userProfessionGlobal` and
  `userProfileTypeGlobal` are plain non-reactive Strings, and the ONLY code that
  ever assigns them is `getUserLoginData()` (shared_preference_utils.dart:788-805)
  and the logout path that blanks them (:557-564). They are populated from
  SECURE STORAGE, never from an API response object.

  A client that patched the profile model in memory would therefore update the
  screen's data and NOT the routing globals — the Me tab would keep rendering the
  old category's dashboard until the next app launch. Please keep that sentence
  in the guide; it is the one instruction that stops this feature shipping broken.

3. GAP A — THE ACCOUNT PLAN IS TAG-SCOPED, AND §8.5 DOES NOT MENTION IT
================================================================================
                                                        *** NEEDS AN ANSWER ***

§8.5 lists "home feed, discovery filters, go-live state, earn/service screens".
It does not mention the Account Plan, and that is the one that breaks.

The plan CATALOG is fetched per tag:

    AccountPlanTag.resolve()      -> userProfessionGlobal (individual)
                                  -> businessCategoryGlobal -> tag id (business)
    AccountPlanController.fetchPlans(tagId: ...)

and a card is marked owned by matching the HELD plan's `option_code` against the
option codes that catalog returned (`ownsPlan`). After a category change the
catalog is a DIFFERENT tag's, so a plan bought under the old tag is not in it.

Concretely, for a Bike Rider holding `GIG_BIKE_PASSENGER` who switches
profession:

  * the Contribution screen shows no Active Plan card — the option_code is not
    in the new catalog to badge;
  * but `AccountPlanEntitlement.hasActivePlan` reads `my-plans`, which is NOT
    tag-scoped, so it stays true and GO-LIVE REMAINS ALLOWED.

The user therefore keeps working while appearing to have no plan. That is a
paid-entitlement question, not a UI one, and we cannot answer it client-side.

  ASK: when a user changes category, what happens to an active Account Plan
  bought under the old tag?
    (a) carries over and stays valid  -> then `my-plans` should keep returning
        it and we need to know how to display it against a catalog that no
        longer contains it;
    (b) is voided / refunded          -> then `my-plans` must stop returning it,
        and go-live must close;
    (c) needs re-purchase             -> then say so in the confirmation sheet
        BEFORE the change, because "some details will be cleared" does not
        prepare anyone to lose a plan they paid for.

Whichever it is, the §5 confirmation sheet copy probably needs to say it.

4. GAP B — STALE HOURS — HALF FIXED IN THE CLIENT
================================================================================

§8.3: "IndividualAvailability is deleted."

Two separate problems. The dangerous one is fixed; the wiring waits on the
feature.

FIXED — `loadHours()` could not clear a DELETED document.
  Both controllers early-returned unless the response carried a Map:

      final data = (body is Map) ? body['data'] : null;
      if (data is Map<String, dynamic>) {
        _hydrateAvailability(AvailabilityData.fromJson(data));
      }                                     // <- nothing happened otherwise

  So when the document is gone, a successful "you have no hours" response left
  the OLD schedule sitting in memory. Forcing a reload would not have helped;
  the force itself was broken. Both now hydrate `null` in that case, which
  clears `weeklySchedule`, drops the today-override and recomputes the shop
  closed:

      _hydrateAvailability(
        data is Map<String, dynamic> ? AvailabilityData.fromJson(data) : null,
      );

  A FAILED request is still left alone, deliberately — a network blip must not
  wipe a schedule that is still there. "The server said there is nothing" and
  "the server did not answer" are different answers and are now treated
  differently.

  Files: view_business_details_controller.dart, view_personal_details_controller.dart

STILL TO WIRE — calling it. Most callers reach hours through
`if (!hasSchedule) await loadHours()`, which only hydrates when nothing is
cached; a stale schedule satisfies that guard forever. `loadHours()` is the
unconditional force path (now documented as such on both controllers), so the
category-change flow must call it DIRECTLY on success rather than relying on the
guard. That is one line in a feature that does not exist yet, and is listed in
§8 below.

  ASK: does a BUSINESS category change also clear business availability hours?
  §8.3 only mentions INDIVIDUAL. The client now handles either answer safely —
  a forced `loadHours()` clears if the document is gone and rehydrates if it is
  not — but the change flow needs to know whether to bother calling it for
  businesses.
